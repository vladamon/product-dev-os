1How it works

The goal is to find a problem worth a product, service or paid pilot inside someone's business, before you have any idea what to build. If there is no such problem, the process should show that too.

prep ──► [rehearse] ──► conversation ──► debrief (same day)
  ▲                                           │  repeat 3–5×
  │                                           ▼
  └──────── directive (what next) ◄──── synthesize

What is fixed, and what adapts

  • The card is not a script. It is a map of topics to cover, plus ready-made follow-ups ("when you hear X, say Y"). You follow the owner's story and improvise the next question. The card shows you what is still uncovered.
  • The plan adapts between conversations. Each debrief records what is still unknown about this business and gives three probes for a short follow-up. Each new prep rebuilds the card around those gaps.
  • Question-by-question adaptation exists too: live mode. Use it on video calls, where a second window does not cost you the owner's attention. In person, use the printed card.

Three rules that matter most

1. Ask about the last time something happened, not what they usually do or would do.
2. Never describe your idea during discovery.
3. Count what they did and paid for, not what they say they like.

2One-time setup (15 minutes)

Install the plugin

You need Claude Code installed and signed in. You also need access to the vladamon/product-dev-os GitHub repository; ask Vladimir if the clone fails.

git clone https://github.com/vladamon/product-dev-os.git ~/tools/product-dev-os
claude plugin marketplace add ~/tools/product-dev-os
claude plugin install product@product-dev-os-local

Create a workspace

Keep all field work in one folder. Every engagement gets its own subfolder automatically.

mkdir -p ~/field-work && cd ~/field-work && git init && claude

Check it works: type /product:field. It should offer to start prep.

Pick a recorder

  • In person: your phone's voice memo app. Most recorder apps can transcribe; otherwise any transcription tool works.
  • Calls: the meeting tool's own transcript (Zoom, Google Meet, Teams), or Granola.

Anything that produces a text transcript is fine. Your own written notes also work, but count as weaker evidence (see section 9).

Updating the plugin

cd ~/tools/product-dev-os && git pull
claude plugin marketplace update product-dev-os-local

Then start a new Claude Code session. A git pull alone does not change what Claude Code loads.

3Prep: before the first conversation (about 10 minutes)

Run /product:field prep inside ~/field-work. Claude asks five questions. Short, honest answers work best.

QuestionWhat a good answer looks like
1. ScopeClient: one business, several people inside it (owner, office, field). Segment: several independent businesses with the same way of working. Define it by behavior ("trades that price every job from supplier quotes"), not by size or industry code.
2. What you can build and runYour skills, hours per week, what you refuse to build (hardware, regulated advice, heavy integrations), and whether you want a product, a service or a pilot.
3. Up to 3 things to learnQuestions to yourself, not to them: "Where do quotes get stuck between the office and the field?" Claude turns each into problem hypotheses and rejects any that already contain a solution.
4. What would change your mindFor each objective: what past behavior would you have to hear to drop it?
5. Language and formatInterview language, in person or call, and the time you will get. Owners often give 10–20 minutes, so plan short sessions.

Prep writes two files in docs/research/field/<engagement>/:

  • engagement.md: the running record. Claude keeps it updated; you rarely edit it.
  • card.md: the one-page interview card, in the interview language. Print it.

/product:field prep pro adds outreach messages per channel (WhatsApp, email, phone), screening questions and a recruiting log.

4Rehearse (optional, recommended the first time)

Run /product:field rehearse. Claude plays a realistic business owner. The persona:

  • talks in generalities ("we usually…") until you ask for the last specific time;
  • praises you, suggests features, and asks "so what are you building?" at least once;
  • hides one real workaround, one key person, one costly exception and one payer who isn't them, revealed only to good follow-ups;
  • says yes to hypothetical pricing, to see whether you count it.

Type end for a report: each of your questions tagged (ok, leading, pitch, hypothetical, praise-seeking, jargon), topics reached, your three weakest questions rewritten, and what the persona was hiding. Add coach to get feedback after every question. Rehearse writes no files.

5During the conversation

  1. Ask before you record. "Mind if I record so I don't have to take notes? It stays with me." If they say no, write notes immediately afterwards.
  2. Open with the card's opener. Keep it under two minutes.
  3. Get one specific, recent episode and walk through it step by step: who, when, what tool, what happened next.
  4. Follow their story, not the card's order. Glance at the card to see what is still unchecked.
  5. Ask to see things: a spreadsheet, a WhatsApp group, a paper form. Take a photo if they allow it. Things you saw count as strong evidence.
  6. At about two thirds of the time, ask the "anything I haven't asked?" question.
  7. Close with a small ask: the last three files, 10 minutes with the person in the office, an introduction to someone else who deals with this.

When you may talk about a solution

Only when both are true: you have a real episode, the workflow, and a workaround or cost from this person, and they agree to switch. Use the card's permission line, for example: "Based on what you described, I'm working on something that might help with that delay. Want to spend five minutes on it, or should we wrap up here?" If they demand to see something, that counts as agreement. Everything said after the switch is tracked separately and never counts as problem evidence.

6Live copilot (video calls only)

Keep /product:field live open in a second window. Paste short fragments of what the owner says. Claude answers in three lines or fewer:

▸ generalizer → ABSTRACT_TO_SPECIFIC
Ask: "The last quote you sent — when did the request come in?"
Coverage: C2 ✓ C3 ◐ C5 ○ C6 ○ · 8/20 min
CommandEffect
time 12/20Minutes elapsed / total; prompts the "anything I haven't asked?" question at 60–70%.
pitchChecks whether you have enough problem evidence to ask permission to switch. If not, says what is missing.
demandThe owner asked to see something; marks the switch.
stuckSuggests the best next topic.
endCloses the log. The log feeds the debrief.

In person, skip it. Typing while someone talks costs you their attention, and attention is what gets you the real story.

7Debrief: same day (about 15 minutes)

  1. Get the transcript out of your recorder or meeting tool.
  2. Drop it into the intake folder, one file per conversation, photos next to it:
    docs/intake/interviews/<engagement>/2026-10-01-mueller.txt
  3. Run /product:field debrief. Claude first asks up to three questions: did you hint at a solution and when, did they give or promise anything, what surprised you. Add pro for two more: what you saw that isn't in the notes, and where you felt yourself leading.

You get a session file in docs/research/field/<engagement>/sessions/ containing:

  • Evidence ledger: verbatim quotes with location and strength level. Claude re-checks every quote against the transcript.
  • The actual workflow as a step table (trigger, who, tool, handoff, wait), every row backed by a quote or marked as inferred.
  • Exceptions, artifacts and workarounds: what breaks, what they built to cope, what it costs to maintain.
  • Commercial severity: frequency × cost × risk, only from numbers they gave; otherwise "unknown".
  • Stakeholders: user, champion, approver, payer, blocker.
  • Unknowns and a resume card with three probes for a 5-minute follow-up.
  • Interviewer check: your leading or hypothetical questions, if they're in the transcript.
  • One directive with a count and a date.

Do it the same day. After a week you will remember "it went well" and not much else, and that counts as zero evidence.

8Synthesize: every 3–5 conversations

Run /product:field synthesize. Claude compares all debriefed sessions, gives its own verdict first (including the strongest case against it), and then asks for your view.

  • One participant can only produce a signal.
  • A pattern needs at least 2 people.
  • Market-validated needs 3 separate businesses. A client engagement can reach client-validated at most, which is enough for a pilot with that client, not for a product.

Every synthesis ends with exactly one directive:

DirectiveMeaningWhat you do next
CONTINUE_INTERVIEWINGNot enough evidence yetRun prep again (the card refocuses on gaps), keep talking
DECOMPOSE_OPPORTUNITYSomething is there, but too broadprep with a narrower segment or problem
TEST_ASSUMPTIONProblem confirmed; solution options existA small paid test or pilot: /product:experiment
HALT_FOR_TECHNICAL_SPIKEThe biggest risk is whether it can be builtStop interviewing; hand the technical check to Vladimir
PIVOTThe pain isn't there, or it's cheapNew segment or objective, or close the engagement

TEST_ASSUMPTION only comes from /product:field synthesize pro, which also builds the opportunity tree and at least three solution options.

9Reading the evidence

Every quote in a debrief gets one level. Only L3 and above count as evidence of a problem.

LevelKindExampleCounts for
L0Opinion, praise"Great idea", "sounds useful"Nothing
L1Hypothetical, wish"I would pay €100", "you should add X"Hypotheses only
L2General claim"We usually…", official policyRanking; must be tied to a real episode
L3Specific episodeA recent event with named people and stepsDesirability
L4Revealed behaviorA sheet you saw, an active workaround, current spendDesirability, feasibility, viability
L5CommitmentDeposit, paid pilot, real files handed over, decision-maker timeViability, traction

A transcript lets quotes reach any level. Notes or a paraphrase cap at L3, or L4 for artifacts you confirm you saw.

12Why this setup (and what comes later)

We considered building a dedicated interview app with live transcription, either inside SpecSmith or on OpenAI's API. We decided against it for now:

  • The value is in the discovery rules, evidence grading and quote checking, which already run in /product:field. A new app would rebuild them in a weaker place.
  • The missing piece is only getting a transcript into the intake folder. Existing recorders already solve that.
  • Most of the value is before the conversation (the card) and after it (the debrief), not in real-time prompts during it.
  • The real bottleneck is the number of conversations, not tooling.

Next steps, only if the current setup still hurts after about 5 real interviews:

  1. Step 1, a glue script (about a day of work): one command records audio, transcribes it, saves it to the intake folder and runs the debrief headlessly with claude -p.
  2. Step 2, a live side panel, only if live prompts prove valuable: a small local page that streams transcription and feeds the live mode, glanceable on a phone or tablet. Still a thin client over the same plugin.
